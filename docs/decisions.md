### D-002 — Authentication and roles
- **Date:** 2026-09-14
- **Status:** Confirmed (default accepted)
- **Decision:** Supabase Auth with email + password. Three seeded demo accounts covering the
  roles Marketing, Sales Manager, and Management (approver). Row Level Security enabled.
  Role gating is visible in the UI — only Management can approve a Sales Approval Form.
- **Why:** The approval step is the core of the commercial flow; a real identity makes the
  demo credible and makes the approval rule enforceable at the data layer rather than as a
  UI illusion.
- **Reversal cost:** Moderate. Auth sits behind the data-access layer, so removal or
  replacement (e.g. with internal LDAP/SSO on-premise) is contained.

### D-004 — Coal price index naming

### D-007 — Price history depth and determinism
- **Date:** 2026-09-14
- **Status:** Confirmed (default accepted)
- **Decision:** Seed **5 years** of daily prices across 4 sources (business days only,
  roughly 1,300 rows per source, ~5,200 total), generated by a deterministic seeded PRNG.

- **Why:** The MoM's stated pain point is comparing today against three years ago. Five years
  covers that with margin. Determinism makes the demo and its tests repeatable.
- **Reversal cost:** Low — change a constant and re-seed.

### D-011 — Technical stack

### D-013 — Local database is plain Postgres, not the Supabase CLI stack
- **Date:** 2026-09-14
- **Status:** Confirmed (product judgement, supersedes the local-stack half of D-003)
- **Decision:** Develop against the Homebrew **postgresql@16** instance already running on
  `localhost:5432` (verified: PostgreSQL 16.11, accepting connections), using a dedicated
  database `crm_isam_dev` and a dedicated non-superuser role `crm_app`. Access via the `pg`
  driver and a connection pool. No Supabase client library anywhere in the codebase.
- **Why:** Docker is not available on this machine, so `supabase start` cannot run. Rather
  than install a container runtime, use plain Postgres — which is what the on-premise target
  actually is. This removes Supabase coupling from the code entirely, so the demo deployment
  can use Supabase-hosted Postgres as nothing more than a connection string, and the
  on-premise path becomes a genuine configuration change rather than a claim.
- **Reversal cost:** Low. The application only needs a `DATABASE_URL`.
- **Note:** A dedicated non-superuser role matters — Postgres superusers bypass RLS, so
  connecting as one would have made the access-control demonstration (AC-09) meaningless.

### D-014 — Authentication is a signed session cookie, not Supabase Auth
- **Date:** 2026-09-14
- **Status:** Confirmed (product judgement, supersedes D-002's mechanism, not its intent)
- **Decision:** Email + password login against a `users` table (scrypt password hashing via
  node's built-in `crypto`), with an HMAC-signed, httpOnly session cookie. Three seeded demo
  accounts covering Marketing, Sales Manager, and Management. Authorisation is enforced in
  two places: a server-side guard on every mutation, and Postgres RLS policies driven by
  `set_config('app.user_id', …)` set per request inside a transaction.
- **Why:** D-002's *intent* was that approval authority be real and enforced at the data
  layer. That intent is preserved exactly. Supabase Auth was only ever the mechanism, and it
  is unavailable locally without Docker — and irrelevant to an on-premise deployment that
  will use internal SSO or Active Directory anyway. Zero new dependencies.
- **Reversal cost:** Low. Session creation is one module; RLS policies are unchanged.

### D-015 — Price index sources
- **Date:** 2026-09-14
- **Status:** Confirmed (product judgement, resolves open question Q-4)
- **Decision:** Four synthetic sources matching the MoM's geography — two Singapore, two China:

- **Why:** Recognisable to a coal audience and geographically faithful to the MoM. ICI-3 and

  normalisation, which is noted as an integration boundary rather than silently ignored.

### D-021 — Deck published to rightjet/hq as a standalone export
- **Date:** 2026-09-14
- **Status:** Confirmed (direct instruction from the project owner)
- **Decision:** The presentation is published to the private repo `rightjet/hq` as
  `crm-batubara/` — a self-contained folder that opens by double-clicking `index.html`: no
  Node, no server, no network. Produced by `npm run deck:export`
  (`scripts/export-deck.tsx`), which renders the same `SLIDES` array the app serves at
  `/presentation` through `renderToStaticMarkup`, compiles the same design tokens via the
  Tailwind CLI, ships a few lines of vanilla JS for navigation, and prints its own output to

  any laptop.

  silently. Rendering from the same source means the export cannot disagree with the deck the
  app serves.
- **Repo shape:** `rightjet/hq` was empty, so this is its first commit. It will hold other
  projects' decks, so the root README documents a per-project folder convention rather than
  leaving the next deck to guess.
- **Reversal cost:** Low — the folder is self-contained and regenerable in one command.

### D-019 — The deck shows real screenshots, captured by script
- **Date:** 2026-09-14
- **Status:** Confirmed (direct instruction: "use screenshots from the demo, the deck has to
  have depth and real")
- **Decision:** Seven slides now lead with **real screenshots of the running application**,
  produced by `npm run deck:capture` (`scripts/capture-screenshots.ts`). The script logs in
  as the demo accounts, navigates the real screens, and photographs individual cards at 2×
  into `public/deck/`. Deck slide count grew from 11 to 18; a new "Biaya dari Proses Hari
  Ini" slide quantifies the current process, and a new "Jalur Menuju Data Harga Sebenarnya"
  slide shows the product declaring its own sources as mock adapters.
- **Why:** A management audience discounts assertions and believes screens. Screenshots also
  keep the deck honest: the "mock adapter" badges and the "DATA DEMO — SINTETIS" chrome are
  visible *in the product*, so the disclosure is shown rather than merely claimed.
- **Why scripted rather than manual:** hand-pasted images rot the moment the UI changes, and
  nobody notices. A capture script makes refreshing the deck a one-line command and keeps the
  slides honest about what the product currently looks like.
- **Captured tight, not full-screen:** a 1440px screen shrunk into a slide column is
  illegible on a projector. The script captures individual cards (via the heading's ancestor
  card element) or the main column without the sidebar.
- **Figures:** every number quoted on a slide is read from the seeded database. The only
  estimates are the email-volume figures (± 1.000/year, ± 3.000 over three years), which are
  arithmetic on the MoM's own facts — 4 sources × business days — and are labelled as
  estimates on the slide.
- **Reversal cost:** Low. Screenshots are regenerable; slide layout is in two files.

### D-018 — Defects found during verification, and what changed
- **Date:** 2026-09-14
- **Status:** Confirmed (record of fixes, not a choice)
- **Decision:** Five defects were found by tests and browser verification rather than by
  reading the code. Each is recorded because the fix changed behaviour:
  1. **Silent RLS refusal on contract writes.** A single `for all` policy made an
     unauthorised UPDATE match zero rows and return success. Split into explicit
     INSERT/UPDATE/DELETE policies so the refusal raises `42501`
     (`db/migrations/0002_loud_write_policies.sql`). A write that is refused must say so.
  2. **Route collision at `/`.** The `create-next-app` placeholder `src/app/page.tsx` shadowed
     `src/app/(app)/page.tsx`, so the dashboard was unreachable and the build marked `/`
     static. Placeholder deleted.
  3. **`pg` pulled into the browser bundle.** `server/action-state.ts` imported the Postgres
     error helpers from `lib/db`, and client components import `IDLE` from it. Helpers moved
     to `src/lib/pg-errors.ts`, which has no driver import. The production build failed on
     this, so it could not have shipped silently.
  4. **`mergeSeries` called across the client boundary.** It lived in a `"use client"` module
     but ran in a server component, which throws at runtime. Pure chart shaping and the
     palette moved to `src/components/charts/chart-data.ts`.
  5. **Ambiguous comparison direction.** `comparePeriods` computed `b - a` while the UI showed
     the result unlabelled beneath both values, so "+12,50" read as though the current period
     had risen when it was in fact lower. Flipped to `a - b`, percentage now relative to B,
     and the UI states the direction in words.
- **Why:** Recorded so the next person does not reintroduce them, and because items 1 and 5
  changed semantics rather than just fixing a crash.
- **Reversal cost:** N/A — these are corrections.
- **Also fixed, minor:** headings on dark slides inherited the base ink colour and rendered
  dark-on-dark; the print-mode slide duplicate is now `aria-hidden` so a screen reader does
  not announce all eleven slides twice; `agentRules: false` stops `next dev` appending a
  generated block to `AGENTS.md`.

### D-017 — Visual design language is Stripe Dashboard
- **Date:** 2026-09-14
- **Status:** Confirmed (direct instruction from the project owner, supersedes the palette
  half of specification §17)
- **Decision:** Adopt the Stripe Dashboard design language: light blue-grey canvas
  (`#F6F9FC`), white surfaces lifted by layered low-opacity shadows instead of visible
  borders, indigo brand accent (`#635BFF`), deep navy-ink type ramp (`#1A1F36` headings,
  `#3C4257` body, `#697386` muted), pill status badges with a status dot, small uppercase

  dark navy one originally built.
- **Why:** Requested directly. It is also compatible with the original intent — §17 asked for
  a restrained enterprise style with no gradients or ornament, and the Stripe language is
  exactly that, executed to a higher standard of craft. For a management audience evaluating
  a local vendor against Salesforce, the perceived build quality of the interface carries
  real weight.
- **Reversal cost:** Low, and it was made lower by doing this now. The change is concentrated
  in `src/app/globals.css` design tokens plus the shared components in
  `src/components/ui/`; pages consume tokens, not raw colour values.
- **Note:** The semantic rule from §17 is unchanged and still binding — colour carries status
  meaning only, never decoration. The amber accent is retained but narrowed to coal-price
  index context.
