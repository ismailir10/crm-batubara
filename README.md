# CRM Batubara — Prototipe Demo

A demonstration CRM for an Indonesian coal trading business, plus a management
presentation deck. Built to support a demo, **not** a production system.

One connected commercial flow:

```
Prospek → Opportunity → Sales Approval → Kontrak → Delivery Order
```

with **Coal Price Intelligence** as the differentiating module.

> **All data in this application is synthetic.** No company, contact, contract or
> price is real. Coal price figures are generated by a mock provider and are not
> market data.

## Setup

```bash
npm install
```

Copy the environment template and fill it in:

```bash
cp .env.example .env.local
```

`.env.local` needs four values:

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Application connection. **Must be a non-superuser role** — see the warning below. |
| `ADMIN_DATABASE_URL` | Owner connection. Used only by the bootstrap, migrate and seed scripts. |
| `SESSION_SECRET` | HMAC key for session cookies. Generate with the command below. |
| `DEMO_PASSWORD` | Password assigned to every seeded demo account. |

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

> **Security note — do not point `DATABASE_URL` at a superuser or the table owner.**
> PostgreSQL superusers and table owners bypass Row Level Security. This
> prototype enforces approval authority through RLS policies, so connecting as a
> privileged role would silently disable that enforcement while appearing to work.
> `npm run db:bootstrap` creates a suitable `crm_app` role for you.

Then create the database, apply migrations and load the demo data:

```bash
npm run db:setup
```

That runs three steps, each of which can also be run on its own:

```bash
npm run db:bootstrap   # create the crm_app role and the database (idempotent)
npm run db:migrate     # apply db/migrations/*.sql in order, once each
npm run db:seed        # load deterministic synthetic data
```

Start the application:

```bash
npm run dev
```

Open http://localhost:3000.

## Suggested demo route

1. **Dashboard** (`/`) — pipeline value, approvals waiting, delivery progress, price strip.
2. **Prospek** → open a buyer → read the meeting notes → follow through to its opportunity.
3. **Opportunity** → change a status with a reason; the timeline records it.
4. **Persetujuan Penjualan** → open a pending form. Point out the **frozen index
   price**: the market reference captured at submission, so management judges the
   price against the market of that day.
5. Sign in as Marketing to show the approve/reject controls are absent, then as
   Manajemen to approve or reject. A rejection sends the opportunity back to
   Pending with the reason attached.
6. **Kontrak** → delivery stages, planned versus delivered tonnage per stage.
7. **Delivery Order** → try a volume larger than the stage's remaining quota; it is refused.
8. **Harga Batubara** → today + 7 days, then Perbandingan Tahun for the multi-year view.
9. **`/presentation`** — the deck. Arrow keys to navigate, `F` for fullscreen.

`npx playwright install chromium`.

### Publishing the deck

`npm run deck:export` produces `dist/deck/` — a self-contained folder that opens
by double-clicking `index.html`, with no Node, server or network. It renders the
same `SLIDES` array the app serves at `/presentation`, so the export cannot drift
from the live deck, and it prints its own output to an 18-page PDF (failing the
build if the page count ever stops matching the slide count).

That folder is published to the private repo
[`rightjet/hq`](https://github.com/rightjet/hq) under `crm-batubara/`. To update
it: re-run `deck:capture` and `deck:export`, then copy `dist/deck/` over
`crm-batubara/` in that repo and commit.

### Deck branding and assets

The deck carries the **Rightjet** mark (`public/brand/rightjet-logo.png`) on the
cover and closing slides. The mark is dark indigo on transparency, so on the dark
slides it sits on a white plate rather than being recoloured.

The application chrome is deliberately *not* Rightjet-branded: Rightjet is the
vendor, the product is for the client. Putting the vendor's logo inside the
product would misrepresent whose system it is.

The presentation deck shows **real screenshots of this application**, not mockups.
They live in `public/deck/` and are produced by `npm run deck:capture`, which
logs in as the demo accounts and photographs the actual screens. When the UI
changes, re-run it with the dev server up and a seeded database rather than
editing images by hand.

## Determinism

Price history is a pure function of `(source code, date)` anchored at
`2019-01-01`, so re-seeding on the same day reproduces byte-identical data, and
seeding on a later day **extends** the series rather than rewriting it. Both
properties are covered by tests in `tests/synthetic.test.ts`.

Verify by hand:

```bash
npm run db:seed && psql -d crm_isam_dev -tAc "select md5(string_agg(s.code||o.observation_date||o.price::text, ',' order by s.code, o.observation_date)) from coal_price_observations o join coal_price_sources s on s.id=o.source_id"
```

Run it twice; the checksum does not change.

## What is real and what is not

**Working in this prototype**

- The full commercial flow, including approval, with role enforcement in the database.
- Coal price history, filtering, period comparison and multi-year comparison.
- Idempotent price ingestion with a per-run audit trail.
- Executive dashboard across all modules.
- The presentation deck.

**Mocked or deferred**

- **Coal price providers.** `MockCoalPriceProvider` only. No connection to the four
  real index servers exists; that needs documentation and credentials. Adding a
  real provider means implementing `CoalPriceProvider` in
  `src/server/price/provider.ts` and registering it — nothing above that boundary
  changes.
- **SAP, MariaDB, the existing PHP CRM, the daily price email.** Not connected.
  Documented as integration boundaries only.
- **Production readiness.** The build is portable (plain Postgres, no vendor client
  library, `output: "standalone"`). Portability is not readiness — on-premise
  deployment still needs internal authentication, network isolation, audit
  logging, backup and monitoring. See `docs/specification.md` §16.
- **Contract documents, e-signature, invoicing, notifications.** Out of scope; see
  the non-goals in `docs/specification.md` §6.

## Known gaps

- Chinese domestic indices are quoted in CNY/tonne in reality. All four synthetic
  sources are held in USD/tonne so period comparison stays on one scale. The
  `unit` and `currency` columns exist per observation, so a CNY source can be
  added later, but it would need FX normalisation.
- The Sales Approval Form fields are a reasonable reconstruction. They should be
  checked against the client's actual form before implementation.
- No visual regression, load, cross-browser or accessibility-audit testing.
